A · Reading the results

A1. "A 5.4 % false-positive rate is too high to deploy." (QA F7)

The FPR is the share of benign files wrongly flagged: 16 of 299 = 5.4 %. In practice, if 1,000 harmless programs run a day, that is about 54 false alarms a day.

  1. It moves a lot with few mistakes. With 299 benign files, each one is about 0.3 points. The 5.4 % is 16 files (§4.1.2 makes FPR a first-class metric because it is this sensitive).
  2. No threshold was tuned. The decision is a fixed argmax (Eq. 4.8, §5.1), so 5.4 % is the untuned operating point.
  3. The trade-off is deliberate. A missed threat can encrypt data; a false alarm costs analyst time (§1.1). Result: 0 of 1,085 threats missed.
  4. It holds on new data: 6 of 200 (3 %) on the unseen-source evaluation.

It's 16 files out of 299, at an untuned operating point, chosen because missing a threat costs far more than reviewing a false alarm. I didn't tune a threshold, so I won't claim what that would give.

A real deployment would calibrate a threshold on its own traffic; confidence calibration is future work (§6.3).

A2. "Exact-class accuracy falls from 285 to 228 without semantics. What does that mean?" (Table 5.8)

Threat recall only asks whether a threat was called a threat. Exact class needs the precise label, so ransomware called "other malware" counts as wrong.

Without semantics the model still catches every threat, but it gets 57 more samples' exact class wrong and flags more benign software. Semantics names the threat; structure catches it. That costs analyst workload, not safety.

A4. "The BiLSTM misses no threat under renaming, so it is robust?"

No. Under renaming it calls every trace a threat: all 200 benign traces flagged, macro-F1 0.136 (Table 5.13). §5.6.2: "an artefact of surrender rather than skill".

A detector that flags everything catches every threat trivially while distinguishing nothing. Its own attack, reordering, it does survive (0.728). Under renaming it cries wolf, and the framework flags only 7 of 200 with no threat missed.

B · Graph and features

B1. "What do you mean by 775 numbers?"

A network reads numbers, not text, so every API-call node carries a vector of 775 numbers:

NtWriteFile  →  [0.021, −0.087, …, −0.031,   0.42, 0.284, 1, 0, 0, 0, 0]
                 └──── 768 from MPNet ────┘   └────── 7 metadata ──────┘
  • 768 MPNet numbers say what the call means. One number alone means nothing; similar calls get similar lists (CryptEncrypt ≈ CryptEncryptEx). Each distinct name is encoded once and reused.
  • 7 metadata numbers describe this occurrence (B2).
  • Resource nodes carry 6 numbers; each temporal edge carries 14 timing numbers (Table 4.2).
  • The first layer projects API nodes 775 → 128 and resource nodes 6 → 64.

Each API call becomes 775 numbers: 768 from MPNet that say what the call means, plus 7 that say when it happened, which process made it, and a coarse category.

B2. "What are the 7 metadata numbers, and what are the flags?"

Two are numbers, five are yes/no flags (enrich_graphs_v2.py:323–334):

PositionFeatureSet to 1 if the name contains…
768time (0 = start, 1 = end)number
769process id ÷ 10,000number
770file flag"file", "read", "write"
771registry flag"reg", "key"
772process flag"process", "thread"
773network flag"socket", "connect", "send"
774crypto flag"crypt", "encrypt"

The flags are crude word matches: WriteProcessMemory gets file + process; CryptGenKey gets registry ("key") + crypto; GetSystemTime gets none.

Why needed: every NtWriteFile has the same 768 numbers. Time and process separate the first write from the thousandth; the flags are a cheap category hint.

In compressed test graphs, columns 770–772 sometimes hold values between 0 and 1; the cause was not traced. Say the flags are set as 0/1 at graph construction.

B3. "Isn't adding the metadata cheating?"

  1. No label leakage. All 7 come from the call record alone (name, time, process), by the same rule for every class, and are available at prediction time.
  2. Sandbox fingerprint risk (most benign samples come from Hybrid Analysis): the 110 unseen-source threats also come from Hybrid Analysis, and all 110 were caught. A model that had learned "this sandbox = benign" would have missed them.
  3. RQ1 substitution kept the flags (only api.x[:, :768] is swapped). But both regimes keep identical flags, so the 0.7 % vs 5.3 % gap comes from the embedding alone; and the random swap still raised missed threats from 8 to 21.

MPNet says what a call is; the metadata says which occurrence it is. It's computed from the call alone, carries no label, and the unseen-source result rules out the model learning the sandbox instead of the behaviour.

How the §5.6 rename attack treats the 7 numbers was not traced; don't claim either way.

B5. "Why does the 110-sample result not prove the flags don't matter?"

The 110 use mostly the same Windows API names, so their flags were computed and present as in training. They test the absence of a sandbox shortcut, not the absence of flags.

C · Structural branch

C1. "How does a graph neural network learn?" (message passing, Eq. 3.2–3.3)

Every node starts with its own vector. In each layer it collects messages from its neighbours, combines them, and updates itself. After two layers a node knows about neighbours two steps away.

Each node asks its neighbours what they are and updates its idea of itself from the answers. GAT and GraphSAGE are two rules for combining those answers.

C2. "How does GAT work?" (Eq. 3.7–3.10)

  1. Score each neighbour j for relevance to node i: eij = LeakyReLU(aᵀ[W hi ‖ W hj]).
  2. Softmax the scores into weights αij that sum to 1.
  3. Take the weighted sum of the neighbours.

Six heads run in parallel and are concatenated (API nodes: 128 × 6 = 768). In this model the projected edge (timing) features enter the score as a third additive term (§4.4.2), so timing changes how much each neighbour counts.

One process spawn or registry-persistence write can matter more than thousands of routine reads. A plain average would bury it; attention can pick it out.

C3. "How does GraphSAGE work?" (Eq. 3.12)

Average the neighbours, join that with the node's own vector, and pass it through one learned layer. No per-neighbour weighting. It is inductive: it learns a rule, not a vector per specific node, so it works on files, processes and endpoints never seen in training.

Your modification: standard SAGE ignores edge features, so timing would never reach it. Here each message is muv = hu + We euv, added before averaging. In SAGE timing changes what a message says; in GAT it changes how much it counts.

Attention scores are learned from the training data, so they are least reliable on neighbourhoods unlike it, which is what a new threat produces. A plain average has less to get wrong there.

C4. "Why both? How are they combined?" (Eq. 4.1–4.2)

StrengthWeakness
GATfinds the one decisive edgeleast reliable on unfamiliar graphs
GraphSAGEstable on unseen graphstreats all neighbours the same
g_v = σ( MLP[ h_GAT ‖ h_SAGE ‖ 2.0 · |h_GAT − h_SAGE| ] )      one value per node AND per feature
h_v = g_v ⊙ h_GAT + (1 − g_v) ⊙ h_SAGE

The gate bias starts at −0.85, so σ ≈ 0.30: training starts 70 % SAGE, because attention scores are random early on. It is only a starting point.

They fail in opposite ways, so both read the same messages, and a gate that looks at where they disagree decides, per node and per feature, how much of each to keep.

C5. "Is it one GAT for the whole graph?" (Eq. 3.5)

No. Each of the 5 relation types has its own hybrid operator with its own weights, two layers, and the results are summed at each node. That is why structural message passing holds 87 % of the 16.1 M parameters: GAT 3.76 M, SAGE 3.73 M, gate 6.50 M (slide 5 carries this line and the formula).

C6. "Why two layers?"

The report states two layers (§4.4.2; NUM_GNN_LAYERS = 2) but gives no depth study.

  • One hop: an API call sees its process, the resource it touched, and the calls just before and after.
  • Two hops: a call sees other calls that touched the same file or ran in the same process; a process sees which resources its calls touched (process → API → file).
  • The sequence-wide order is read by the BiLSTM, so the graph layers need not reach far along the chain.
  • Every layer adds weights for all five relations; graphs reach 1.5 M API nodes before capping.
  • The GCN and GAT baselines also use 2 layers (§5.1.3), so the comparison is like for like.

Two hops joins a process, through its calls, to the files, keys and endpoints they touch. Long-range order is the BiLSTM's job. I didn't tune depth, and I'd say so.

Over-smoothing with many layers is general GNN background, not something the thesis tested.

C7. "Why not only GraphSAGE?"

  1. Sparse evidence. SAGE "treats all neighbours of a relation uniformly and therefore cannot emphasise the rare, salient interaction" (§4.4.2). One persistence write among thousands of reads is diluted.
  2. Timing enters GAT's weighting. In SAGE timing is only added to the message.
  3. The gate kept using GAT. The mean moves 0.30 → 0.28 but the spread doubles: GAT is used strongly on some nodes. If it were useless the gate could have switched it off.

GraphSAGE alone would average away the one edge that matters. GAT can single it out, and timing feeds its weighting. The gate starts mostly SAGE and learns, node by node, where attention is worth trusting.

No SAGE-only or GAT-only variant was trained; there is no measured gain from adding either.

D1. "Give an example of where GAT helps and where SAGE helps."

Illustrative of the design intent; the thesis reports only the gate's mean and spread, not per-node usage.

GAT: one edge decides, in a familiar neighbourhoodSAGE: unfamiliar neighbourhood, or volume is the evidence
Process injection: hundreds of routine executes edges plus one WriteProcessMemory / CreateRemoteThreadA new threat from a new source (RQ5's 110 threats)
Persistence: thousands of registry reads and one write to a Run keyMass file activity: a process writing thousands of files the same way
Encryption burst on the temporal spine: gaps under 0.1 s, weighted up via the edge featuresNew files, endpoints, processes never seen in training (inductive)
One network contact among many file operationsEarly training, while attention scores are still random

If one persistence write hides among a thousand reads, attention finds it. If the whole neighbourhood is new, or the evidence is a thousand similar writes, the average is the safer read. The gate decides which situation each node is in.

E · Fusion, trunk and decision

E1. "How are the branch weights computed? What is the MLP?" (Eq. 4.3–4.4)

MLP = multi-layer perceptron, a small ordinary network (tgnn_model.py:373–379):

[z_sem ‖ z_str ‖ z_tmp]  (128+128+128 = 384)
  → Linear 384→128 → LayerNorm → GELU → Dropout → Linear 128→3 → softmax  =  w (3 weights, sum to 1)

The MLP only produces the weights. Fusion is plain arithmetic with no learned weights: each weight multiplies all 128 numbers of its branch.

z = w_sem·z_sem + w_str·z_str + w_tmp·z_tmp
toy: 0.66·[0.9, 0.1] + 0.15·[0.2, 0.3] + 0.19·[0.4, 0.6] = [0.70, 0.225]

How does the MLP "know the context"? Its input is this sample's own 384 numbers, and training taught it which weighting reduced the loss for inputs like these. Semantics averages 0.661 for ransomware and 0.223 for benign; nobody set those values.

For every sample, a small network reads the three branch summaries and outputs three weights that sum to one. The fused vector is their weighted mix.

E2. "Doesn't the entropy penalty force balanced weights?" (Eq. 4.5, QA F2)

L_bal = 0.01 · max(0, 0.75 − H(w)/log 3)        H(w) = −Σ w_i log w_i

The 0.75 is a threshold on normalised entropy (0 = all on one branch, 1 = even), not a 75 % weight.

Gate weightsEntropyPenalty
(0.35, 0.35, 0.30)≈ 0.9980
(0.66, 0.15, 0.19)≈ 0.800

How the model "amends" it: the penalty is added to the loss; its gradient nudges the gate MLP towards spreading weight. At λ = 0.01 it is tiny, so the classification loss overrides it whenever specialising actually helps.

It's zero unless the weights become almost one-hot, and the gate moves freely inside that range. I'll concede it rules out near one-hot weights like 0.8 / 0.1 / 0.1.

The report's reason is preventing collapse "before the slower-converging branches have become informative" (§4.4.4); it does not name which branch is faster. Branch dropout (0.05) is drawn once per batch in the code, not per sample; say "per training step".

  • Behavioural statistics: for each of 5 node types, mean and spread of its hidden states (each one number) and log(1 + count) = 15 numbers. Averaging hides volume (5 files and 5,000 files can pool the same); these restore it. Not normalised in the reported checkpoint.

E4. "What is fixed in advance, and what is learned?"

Fixed by designLearned in training
3 heads, 128 → 1 each; class order; softmax + argmax + binary projection; all layer sizesEvery weight and bias: 129 per head (387 for all three), and all 16.1 M parameters; saved in best_model_1.pt and frozen

Three Linear(128 → 1) heads are mathematically the same as one Linear(128 → 3); it is a code choice. The trunk's and heads' weights start random; the gradient of the loss pushes the true class's head score up and the others down.

F · Training, then prediction, step by step

Phase A · Build the dataset (once)

  1. Collect reports: Carpenter–Luo CAPE reports (VirusTotal labels) plus Hybrid Analysis (mainly benign, plus recent threats).
  2. Normalise both formats into one; de-duplicate resource references; filter background network traffic.
  3. Discard traces with fewer than 10 API calls; tag each as rich, low-activity or very sparse.
  4. Build the graph: one node per call, temporal edges between consecutive calls, resource nodes linked by executes / operates_on / modifies / connects_to.
  5. API nodes: MPNet(name) 768 + 7 metadata = 775. Resource nodes: 6.
  6. Temporal edges: 14 timing features.
  7. Compress identical back-to-back calls under 1 s apart; cap graphs over 100,000 nodes to 30,000, protecting cross-type and spike-adjacent nodes.
  8. Split 9,333 graphs 70 / 15 / 15, stratified; withhold the extra held-out threats and the 110 unseen-source threats.

Phase B · Create the model

Read the schema (node types, relations, feature sizes) and build every layer. All 16.1 M weights start random, except the GAT/SAGE gate bias, set to −0.85.

Phase C · One training batch

  1. Pick samples: oversampling weights 9.0 ransomware / 3.5 benign / 1.2 other malware; size-aware batches (64 small graphs, down to 1 above 100,000 nodes).
  2. Vary them (training only): graph augmentation (feature noise, some edges withheld, more often for rarer classes); timing noise with p = 0.2, σ = 0.05.
  3. Forward pass: projections (775 → 128, 6 → 64) → semantic mean → 2 hybrid message-passing layers → structural mean → BiLSTM (2 layers, 126 per direction) + 6-head attention pooling → branch dropout 0.05 → gate → fusion → +15 statistics → trunk → 3 heads → softmax.
  4. Loss: focal loss −α(1 − p)²·log p, α = (0.39, 0.39, 0.42), plus the balance penalty. Easy sample p = 0.9 → factor 0.01; hard p = 0.3 → 0.49.
  5. Backward pass: the gradient of the loss for every weight.
  6. Update: clip gradients to norm 1.0; AdamW step, learning rate 10⁻⁴, weight decay 10⁻³.

Phase D · After each epoch

  1. Validate (no learning, no dropout, no noise): macro-F1 and per-class recall.
  2. Save only if macro-F1 is the best so far and ransomware recall ≥ 0.40 and benign recall ≥ 0.52.
  3. Reduce the learning rate on plateau.
  4. Stop after 20 epochs without improvement, or at 125 epochs. The kept checkpoint is best_model_1.pt.
  5. Test once on the untouched test split with the binary projection: 0 of 1,085 threats missed, 16 of 299 false alarms.

Phase E · Prediction for a new report

  1. Get the sandbox JSON report.
  2. Same preparation as Phase A (pipeline_v2: adapter → builder → enricher). An unseen API name is simply encoded by MPNet.
  3. Load best_model_1.pt in evaluation mode: dropout, augmentation, noise and branch dropout off; no loss; weights frozen.
  4. One forward pass → 3 probabilities → argmax → threat / benign. No tuned threshold.
  5. Explain: gate weights plus gradient × input saliency (G).

G · RQ4 attribution

G1. "How is attribution calculated?"

Level 1, gate weights: read directly from the forward pass (model._last_branch_weights). They are the exact coefficients used to build z for this sample. Thesis example (§5.8, Fig. 5.10, slide 12; held-out malware, threat at 0.95): temporal 0.39, structural 0.31, semantic 0.29.

Level 2, gradient × input saliency (compute_gradient_x_input_saliency, explain_rq4_behavioral_decisions.py:595):

  1. Copy the API node features with gradient tracking on.
  2. Forward pass; take the predicted-class logit.
  3. score.backward(): a gradient for each of the 775 numbers of every API node.
  4. Sv = Σd | xv,d · ∂score/∂xv,d |, one score per call.
  5. Divide by the largest, so the top call = 1.0.
Toy callxgradientx × gradientSnormalised
NtDuplicateObject[0.10, −0.05, 1.0][2.0, 1.0, 0.8][0.20, −0.05, 0.80]1.051.00
GetSystemTime[0.08, 0.02, 0.0][0.5, −1.0, 3.0][0.04, −0.02, 0.00]0.060.06

A large gradient on a feature whose value is 0 contributes nothing; that is why the gradient is multiplied by the input.

Thesis result: NtDuplicateObject (maximum), NtAddAtomEx / NtFindAtom, setsockopt, NtOpenEvent, CryptCreateHash / CryptDestroyHash, NtSetInformationFile; in bursts, from the sample's own process.

Level one reads the gate's three weights: which kind of evidence. Level two back-propagates the predicted-class score to every API node and multiplies gradient by input: which calls pushed it. Both are quantities the model computed for this decision, not a separate explainer.

§5.8 describes "the gradient of the predicted-class score"; the code computes gradient × input, so use that term. It is an interpretability aid, not causal proof; one illustrative sample, but the method runs on every prediction (the webapp does it per upload).

G2. "The gradient is for that sample? And what is the input?"

Yes: the gradient comes from this sample's own forward pass. The input is the 775 numbers on each API node as they enter the model (api.x, before projection), not the text and not the raw report. Only API nodes are scored; resource nodes and edge timing are not.

Every NtWriteFile shares the same 768 MPNet numbers, yet occurrences get different saliency, because their gradients (graph position) and 7 metadata numbers differ. Saliency picks out which occurrence mattered.

H · "Why X and not Y?" design questions

Already in QA_prep.md: BiLSTM vs transformer / Mamba (C2), bidirectional (C3), semantic mean (C1), three classes (C4, G5), focal α (C5), recall floors (C6), regularisers (C9), batching (C10), heterogeneous (C12), R-GCN / HGT (F9), MPNet on names (F8), TF-IDF baseline (F6), attention as explanation (C8).

Representation
Why MPNet, not BERT, CodeBERT or word2vec?As a sentence-transformer it is trained so similar meaning gives close vectors, which renaming robustness needs; plain BERT gives poor sentence-level vectors without that (§3.9). Encoders were not compared.

Behavioural statistics: a hand-crafted shortcut?Pooling hides volume. They are counts, means and spreads of the model's own node states, available for every sample, with no label (§4.4.5).
Why log counts?Counts span 10 to 30,000+; without the log the largest graphs dominate.
Training and evaluation
Focal loss, not weighted cross-entropy?Weighting changes how much each class counts; focal also down-weights easy samples, so training focuses on hard ones, mostly minority-class (§4.5.1).
Macro-F1 for checkpoints, not threat recall?Threat recall alone rewards flagging everything (the BiLSTM's crying wolf). Macro-F1 weighs all classes; the floors guard the minority classes.
Gradient × input, not SHAP, GNNExplainer, Integrated Gradients?The model's own gradients, one backward pass, no separate explainer. Not compared; §5.8 calls it an aid, not causal proof.
Random stratified split, not time-based?A time-based split was not done. The distribution-shift test is RQ5 (different sandbox and source). For leakage, see QA B4.
Why AdamW, learning rate 10⁻⁴?Standard, stable settings, with gradient clipping at 1.0 for the wide range of graph sizes. Not tuned by search.

I · The classical baseline's features

I1. "You crippled the classical baseline by giving it only TF-IDF tokens." (QA F6)

The baseline uses TF-IDF unigrams and bigrams of the API sequence (TfidfVectorizer(ngram_range=(1,2), max_features=3000)).

  1. TF-IDF n-grams are the standard published representation for this family, not a strawman.
  2. The attack (behaviour-preserving renaming) is a real evasion technique.
  3. The code also has a frequency-dilution attack (prove_classical_model_attacks.py) aimed at count-based features, so counts do not escape either.
  4. Its real weakness is token identity: it collapses under rename (275 missed) and survives interleaving (4 missed).

"What else could it have used?" API call counts or frequency histograms; per-category counts (file, registry, network); behavioural totals (processes, files written, keys modified, endpoints contacted); timing statistics (mean gap, burst ratio); graph statistics (node counts per type, degrees). Static PE features were excluded by design (behavioural focus, §4.1.1).

Anything keyed to call names, counts included, falls to renaming or dilution, because the identity it counts is what the attack changes. The framework survives because it reads meaning, structure and timing together.

None of those richer feature sets was tested; don't claim they would also fail, only that name- and count-keyed features are exposed to the attacks run.
